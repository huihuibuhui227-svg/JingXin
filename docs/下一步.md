1. **"测试通过 ≠ 有约束力"这一路反复出现**。形态:抽样唯一性断言、fixture 恰好 100 字导致分母
   可被删掉、空输入契约无守卫、`listen_for_speech` 的新规则是死代码、只认 query 的 id 会静默
   降级成 NONE、**断言用了裸词「不同」而报告别处本来就有「不同指标的量纲……」**(I4 收尾时我
   自己踩的)。
   - 强制动作:**每个测试都要能说出"哪个生产改动会让它变红、红得对不对"**;说不出来就是没约束力。
   - 已常驻:`tests/test_assert_coverage.py` —— 但**它抓不到"缺断言"**,别当万能。
2. **反向复现是标准动作**:写完后把生产改动撤掉(整文件回退 / 外科式抽掉接线),确认新测试
   真的红,再恢复。本轮 5 项逐项做过。
3. **变异验证必须清 `__pycache__`**:同一秒内"写入→跑→`git checkout` 还原"会**跑变异字节码**。
4. **阈值/常量一律进数据文件**(带 `_provisional` + 依据)。注意**单位错配**:门槛是给帧级列设的
   (一场上千帧),而「连接词密度」每段回答一个样本、题库仅 8 题 → 该族单独登记 **5**。
5. **跨任务集成点要在计划里点名**:T3 改文件名没把 `data_loader` 的选取正则列进改动面,导致报告
   路径什么都加载不到 —— 只有审查者用真加载器跑了一遍才发现。
6. **文档口径要一起改**:I3 就是"spec/计划说 ≥2 段、代码门槛是 5"这种互相矛盾,靠 grep 才抓得到。
   **但账本里的历史记录不改** —— 改了就成篡改。
7. **WSL 内删文件不还 Windows 磁盘**:`D:\WSL\ext4.vhdx` 只增不减,回收需 Windows 侧
   `wsl --manage <发行版> --set-sparse true` 或 diskpart compact。
8. **验收要先指明"验的是哪个产物"** —— 前端 `npm run build` 在每一个提交上都失败(第 25 条),
   却因为每轮都在**工作树**里跑而"通过"了若干次。能在隔离快照里跑的
   (`git archive HEAD | tar -x -C /tmp/…`,再软链 `node_modules`),就不要在工作树里跑;
   报"通过"时必须说清是对哪个 commit / 哪份快照。这是 §4.1「测试通过 ≠ 有约束力」的上一层:
   **测试再硬,跑错了对象也一样。**
9. **提交前先点名"哪些文件里装着使用者的未提交工作"** —— git 按文件暂存,一个文件里同时有我的
   改动和使用者的 WIP 时,`git add <文件>` 会把 WIP 一起带上(2026-09-25 `5aa63c0` 就把使用者
   未提交的 `ReportPage.tsx` 整页重写一并提交并推送了)。**技术上绕得开**:造 patch 后
   `git apply --cached`,或 `git hash-object -w` + `git update-index --cacheinfo` 精确暂存
   (本次 `28476df` 即如此 —— `AnswerInput.tsx` 里使用者的 `bordered→variant` 留在工作树未混入)。
   **但绕得开不等于可以不说:提交前必须先讲明并请使用者裁定。**
10. **接线时"上游产出名 ≠ 下游列名"= 静默的零值**(N1 实测,本轮最大的坑)。
    `ProsodyFeatureExtractor` 吐 `pitch_std`/`energy_std`,而**日志列**叫
    `pitch_variation`/`energy_variation`;改名**只发生在** `ProsodyAnalyzer` 里。
    于是"把提取器接上"这件事**看起来做完了**(其余每一列都对),而那两列**安静地留 0**。
    - 强制动作:接线时**逐个键对一遍**上游产出与下游消费(可写成断言:上游产出的键
      必须"要么本身就是下游列,要么在改名表里")。
    - 并钉一条**只守改名**的测试 —— 别并进"值非 0"那条,否则红了看不出是这个原因。
11. **读代码要读到"覆盖它的下一条":诊断要对着净行为,不是对着那一行**(N1 顺带查出,§3 第 33/34 条)。
    `pitch_variation` 的封停理由写「实际取的是 pitch_mean」—— 那是对着**那一行别名**下的结论,
    而那一行**后面还有一次通用数值扫描把它覆盖掉**,净结果其实是**正解**;
    同一段代码**只把两列先后换一下**,又会真的取错。
    **"这行会做 X" ≠ "结果会是 X"。** 下结论前先把覆盖关系读完,并用**交换输入顺序**
    这类最小扰动实测一次 —— 顺序敏感的分支,今天对可能只是**碰巧**对。
12. **"今天没人调" ≠ "它不会说话":判死代码要判**能不能**被调到,不是**有没有**被调到**
    (§3 第 28 条实测)。那套无出处的韵律阈值判语,活路径确实喂不出 prosody
    —— 但写入 `qa_pairs` 的那个函数 **`add_qa_pair()` 接受 prosody 参数**,
    于是它是一颗**随时能引爆**的雷:喂一个假对象,它立刻按阈值吐出
    「语调起伏大,富有表现力」。**判定"死代码"时,要看的是它的入参有没有活着的来源,
    而不是当前调用方传了什么。** 传参口还开着 = 雷还在。
    钉子:`tests/test_no_baseless_prosody_verdicts.py` —— 它**主动喂 prosody**
    去引爆,而不是只验"现在没人传"。

## 8. 工具成本与效率(2026-09-25 中秋,实测)

**这一节跟 JingXin 系统本身无关,是 Claude Code 自身的开销。** 起因是 7 天账单折算后烧钱明显,
用 `session-report` 插件实测了一次。

**窗口:2026-09-19 ~ 09-25,16 场会话 / 14,043 次 API 调用 / 活跃 21.3 小时。**

### 8.1 成本模型:只有这一条公式

> **成本 ≈ 平均上下文 × 调用次数 × 单价**

实测:**145,428 token/次 × 14,043 次** = 20.5 亿 token。但 **98.4% 是缓存读取**。

按 DeepSeek 官方价(缓存命中 0.02 / 未命中 1 / 输出 4 元每百万 token,空闲时段):

| 项目 | 量 | 单价 | 成本 | 占比 |
|---|---|---|---|---|
| **缓存读取** | 2,018.3M | 0.02 | **40.4 元** | **40.7%** |
| 未缓存输入 | 23.9M | 1.00 | 23.9 元 | 24.1% |
| **输出** | 8.7M | 4.00 | **35.0 元** | **35.2%** |
| | | | **≈ 99 元/周** | |

**⚠️ token 份额 ≠ 成本份额。** 缓存读取占 98.4% 的 token,但单价只有 1/50,成本占比 40.7%。
**看报告不能只看总量。** 叠加峰谷后实际约 **134 元/周 ≈ 580 元/月**。

### 8.2 可优化的(按性价比排)

**① 峰谷挪时间 —— 免费,省最多 ★**

高峰时段(工作日 9:00-12:00、14:00-18:00)单价**全部 ×2**。实测工作时段:

```
9/22 周二  20:32-23:22   593M   空闲
9/24 周四  10:56-14:35   701M   ⚠高峰   ← 全周 34% 在这
9/24 周四  19:40-23:28   501M   空闲
```

**周四白天那一场是唯一的大额高峰消费。同样一场活挪到 18:00 之后跑,估计省 15–35 元/周。**
零成本、零风险、不用改任何配置。

**② 别让单条 prompt 跑到上千次调用**

| 调用次数 | 平均上下文 | prompt |
|---|---|---|
| **3,348 次** | 78,340 | `测评提示词_心理学专家审查.md` |
| 1,146 次 | 120,445 | `看一下jingxin下一步,开始下一步任务` |
| 1,077 次 | 147,470 | `继续,T5 该派就派` |
| 801 次 | 161,476 | `继续,T3 该派就派` |

一条 prompt 跑 3,348 次 = 每次都重读一遍上下文。**中途 `/clear` 或分段推进,直接把这条腿砍短。**

**③ 「该派就派」这个句式要加边界**

它在头部出现两次,合计 **14%**。而 **9,795 / 14,043 = 70% 的 API 调用来自 general-purpose
子代理**(78 个,平均每个跑 **126 轮循环**)。这句话明确授权了开放式扇出。

改法:派之前写死边界 —— **"派一个做 X,只返回 Y,不要继续探索"**。

**④ 上下文窗口(评估过,不建议动)**

配置是 `CLAUDE_CODE_MAX_CONTEXT_TOKENS: 1000000` + `deepseek-v4-flash[1M]`,实测有 prompt
平均 **331,436 token/次**(`按这个来,保留审查者,开工…`,333 次),1M 上限让它一直不触发 compact。

降到 250k–300k 理论上能压缓存读取,**但 compact 更频繁 = 更容易丢上下文,且压缩本身也耗 token。
收益不确定,不动。**

### 8.3 不该优化的(别白费力气)

- **输出那 35.2%**:8.7M ÷ 14,043 = **623 token/次**,这是写代码/写分析/写审查的正常产出量。压不动,硬压只会让活干得糙。
- **缓存单价已经 0.02 元/M**(全价 1/50)。优化空间在"量"不在"价",而"量" = 上下文 × 次数。
- **subagent 不全是浪费**:它隔离上下文,本身在保护主会话。真问题是任务规模,不是手段。

### 8.4 一个对账警告
