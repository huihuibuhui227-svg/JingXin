## 1. 为什么需要这一步(问题陈述)

「L0 = 54 列」这个数在文档里说了很多遍,**但那 54 列是什么,从来没有被写下来过。**
2026-09-26 全机核实(仓库 `docs/`、`~/jingxin-下一步.md`(9-21 原始版)、共享盘、记忆目录):

- 全库搜「54 列」命中 6 处,**全部是计数引用**,没有一处展开成列表
  (`2026-09-21-...-design.md:277-283`、`2026-09-22-...-evidence-gate-...md:108,120,136,402`、`下一步.md:432,517,824`)。
- 文档实际给的是**一张旧列处置表**(旧 191 列按 保/修/重构/删 标记),**不是新列的枚举**。
- **三处计数对不上,且对不上的方向都是"推不出来"**:
  - **语音**:文档说 ≈16 列,而 `§4.3`(`:233-239`)只列了 10 个旧列,扣掉 `speech_ratio`(删)、
    `duration_sec`(移出)后**只剩 8 个** ⟹ 推不出 16。
  - **手势**:文档说 ≈13 列,而 `§4.2`(`:215-227`)**整张表没有「L0 形态」这一列**
    (面部两张表有),只给了处置与依据 ⟹ 推不出 13。
  - **面部**:文档说 ≈22 列,`§4.1`(`:161-211`)标 保/修/重构 的**行**共 22 行 —— 但把这 22 行
    变成 22 **列**,要做**两个文档从未声明的决定**(iris 一行拆成 4 列;不计入 `is_valid`/
    `session_id`/`timestamp` 三个非测量列)。
- `9-21` 的原始版 `~/jingxin-下一步.md:178` 写的是同一句
  `面部 ≈22 列 / 手势 ≈13 列 / 语音 ≈16 列` ⟹ **这三个数是第一天的估数,从没被核实过。**

**结论:「≈54 列」不是一个能开工的任务。** 现在开工,等于由实现者**临场替文档编出这 54 个量的
定义** —— 而这正是本项目一直在杀的那个形态(`下一步.md` §4.12「传参口还开着 = 雷还在」同族)。

**本里程碑要交付的不是"重构 54 列",而是"那 54 列到底是什么"** —— 并且让它**能被机器检查**,
而不是靠人记得。

## 2. 目标与非目标

### 2.1 目标

1. 产出**一张 L0 列清单**:每一列都有 `定义 / 来源 / 归一化 / 量纲 / 成熟度 / 验收判据`。
2. 这张清单**能被执行的东西检查**:产出里多一列、少一列,测试红。
3. 顺手清掉清单里**已经能定的两条**:补 5 个"文档要求但零实现"的新列;删手势那 4 个死代码文件。
4. **合并门 `0 / 2835510` 必须仍然过**(动采集层就得重跑,见 §7.3)。

### 2.2 非目标(明确不做,防止范围蔓延)

- **不做任何一列的语义重定义** —— 那是 M3.2(面)/ M3.3(手)/ M3.4(语)的活。
  本里程碑只**写下应该是什么**,不改现有实现。
- **不做 L1(36 个指标)、不做阈值、不做标定** —— 阈值来自标定集,归 M5。
- **不动 `evidence_gate.py` 的 35 条封停** —— 本清单要**引用**它们的 `unblock`,不解封它们。
- 不重跑论文、不动 `experiments/` 的离线数据集线。

## 3. 交付物

### 3.1 一张表,落成**数据文件**(不是 markdown 表格)

**落点**:`l0_columns.json`(仓库根,**与 `media_retention.py` / `session_meta.py` 同层**)。
选根目录的理由与那两个相同:**三服务 + 报告层共用的横切事实**,不属于任何一个模态包。

**每行一个字段**:

| 字段 | 含义 |
|---|---|
| `column` | 列名(日志里逐字出现的那个) |
| `modality` | `face` / `gesture` / `voice` / `text` / `covariate` |
| `definition` | **可执行的**定义:公式、landmark 下标、或明确的算法 |
| `source` | 数据来源(哪个模型输出 / 哪个 landmark / 哪一段音频) |
| `normalization` | 归一化分母与依据;无归一化则写 `none` 并给理由 |
| `unit` | 量纲(比值 / 度 / 毫秒 / 计数 / 米) |
| `maturity` | `A` / `B` / `C`(判据见 §4.2) |
| `l0_output` | **这一列 L0 实际吐什么**(C 档必填:吐原始一阶量,阈值留给 L1) |
| `status` | `implemented` / `pending` / `blocked` |
| `quarantine_ref` | 若该列关联 `evidence_gate.QUARANTINE` 的某条,写下那个键与它的 `unblock` |
| `acceptance` | **这一列怎么算"重构好了"**(见 §6) |

**为什么不是 markdown 表格**:markdown 表格**没有约束力**。项目已经栽过
「spec 说 ≥2 段、代码门槛是 5」这种互相矛盾、靠 grep 才抓到(`下一步.md` §4.6);
也栽过「文档写了、没人实现」(本文件 §1 的 5 个零实现新列就是活证据)。
数据文件 + 钉子 = 这条矛盾**不可能静默存在**。

### 3.2 钉子:`tests/test_l0_column_table.py`,**双向覆盖**

两条方向都要红,缺一条这个钉子就没约束力:

- **方向 1(产出 ⊆ 表)**:采集层三份日志的列契约
  (`face_expression/utils/logger.py:43-59`、`gesture_analysis/utils/logger.py:57`、
  `voice_interaction/utils/logger.py:48`)+ `feature_engine` 的派生键,
  **每一个都必须能在表里找到**;找不到的必须出现在一个**显式的 `legacy_allowlist`** 里。
  ⟹ 谁往日志里加一列而不进表,**测试红**。
- **方向 2(表 ⊆ 产出)**:每一行标 `status: implemented` 的,**必须真的出现在产出里**。
  ⟹ 谁把表里标了"已实现"而其实没实现(或后来被删掉),**测试红**。

**反向复现(强制)**:写完后把生产改动撤掉(从日志契约里删一列 / 把某行标成 `implemented`),
确认钉子**真的红**,再恢复。做不到这一条就是没约束力(`下一步.md` §4.2)。

## 4. 关键结构决定

### 4.1 ★ 把「L0 输出什么」与「L1 判什么」**分开写**

**这是让本里程碑不卡住的那个决定。**

文档里有相当一批列的定义写着"**由标定定**"(`au1` 是否减视频内中位数)、
或依赖标定集的分位(`au12 > p90(au12)`、`au26` 的 `p1/p99` 映射)。若把"这个阈值还没定"
当成 L0 的欠债,**整个 M3 会被 M5 阻塞**。

正确切法:**L0 只输出一阶量,阈值是 L1 的输入。**

- 例:`au26_jaw_drop` —— L0 吐「(下巴−上唇竖直距) ÷ face_height」这个**比值**;
  `p1/p99 → [0,1]` 的映射**等标定**,写进 `l0_output` 栏说明这一列当前吐的是什么。
- 这与上游 spec 自己的分层一致(`:110`:「L0 采集层只输出一阶、按解剖尺度归一、
  时间基准统一、缺失可辨识的量」)。

⟹ **成熟度 C 的列不是阻塞项**,而是"定义已定、阈值待定"的列。

### 4.2 成熟度三档(判据必须可判定,不许含糊)

| 档 | 判据(必须**同时**满足) | 现在能不能实现 |
|---|---|---|
| **A** | ① 定义含公式或精确 landmark 下标 ② 含归一化分母 ③ **不需要任何标定集常量** | ✅ 直接实现 |
| **B** | 定义完整度不足,但**缺的只是一个现在就能定的参数**(算法 / 下标 / 分母),**不需要标定数据** | ✅ 定完写下依据即实现 |
| **C** | 定义里有一个量**只能来自标定集**(阈值、分位映射范围、事件门限) | ✅ L0 吐原始一阶量,阈值留给 L1 |

**灰区规则**:一条列若同时像 B 又像 C,判 **C** —— 保守方向是"留给 L1 一条原始量",
而不是"现在编一个阈值"。上游 spec 的硬规矩支持这条:**禁止用视频内分位定义事件**
(`:294` 规矩 1:`au12 > p90(au12)` 按定义永远选 10% 的帧,与 `speech_ratio` 的自指同类错误)。

### 4.3 「54」这个数要以**算出来的**为准,并登记与文档估数的差

文档的 22 / 13 / 16 / 3 是估数(§1 已证)。本里程碑**以逐列定义的结果为准**,
并在表头登记一个 `count_reconciliation`:文档估数 vs 实际数,以及**每一处差异的原因**。
不许把估数悄悄改成实际数而不说明 —— 那是篡改口径(`下一步.md` §4.6 的另一半)。

## 6. 验收判据(本里程碑"做完了"是什么意思)

1. **`l0_columns.json` 里每一行都有结论**:`maturity` ∈ {A,B,C}、`definition` 非空、
   `acceptance` 非空、`status` ∈ {implemented,pending,blocked}。**任何一格留空 = 未完成。**
2. **双向覆盖钉子两条方向都实测红过**(反向复现记录进账本)。
3. **`count_reconciliation` 存在**,且文档估数与实际数的每一处差异都有原因。
4. **合并门 `0 / 2835510` 逐位不变**(§7.3)。
5. **全量套件**(基线 410 passed)不减少;新增钉子计入。
6. 那 5 个"零实现"的新列:`status` 从 `pending` 变 `implemented`,**且产出里真的出现**。
7. 手势那 4 个死代码文件:**删除后全仓无 import 断链**,且 `npm run build` / 套件不受影响。
